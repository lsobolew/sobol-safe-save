# Working in this repository

This is **Sobol Safe Save**, built on WP Plugin Lab: a WordPress plugin development environment plus the
plugin it builds.

Sobol Safe Save warns people before they save that WordPress is about to strip part of their content, and
never blocks the save. `plugins/sobol-safe-save/EXTENDING.md` documents the surface a paid add-on builds
on; read it before changing any hook or the shape of the analysis payload.

## Read the skills first

`.claude/skills/wp-plugin-lab` describes this repository's CLI and workflow,
`.claude/skills/create-wp-plugin` covers starting a new plugin from it, and
`.claude/skills/wp-org-release` covers readme.txt and publishing to the WordPress.org directory.

The rest of `.claude/skills/` is the official
[WordPress agent skills](https://github.com/WordPress/agent-skills) project.
They cover plugin architecture, REST APIs, blocks, WP-CLI, performance and the WordPress.org
directory guidelines. Consult them before writing WordPress code - they are more current than
anything memorised.

Keep them fresh with `./bin/wpx skills update` (a weekly CI job opens a PR for the same thing).

## Golden rules

1. **PHP only runs in containers.** The host has no working PHP. Never suggest `composer`,
   `phpunit`, `phpcs` or `wp` as host commands - use `./bin/wpx sh <target> -- '<command>'` or the
   dedicated `wpx` commands.
2. **Never run `wp plugin install` against a mounted plugin.** `plugins/` is bind-mounted into
   every container; WordPress deletes the target directory before unpacking, which destroys the
   working copy on disk. Use `./bin/wpx build --verify`, which unpacks into a throwaway directory.
3. **Changes must be proven on more than one WordPress version.** Anything touching rewrite rules,
   the block editor, REST or multisite gets tested with `./bin/wpx test --targets=latest,min`
   at minimum. The matrix exists because those are exactly the things that break.
4. **Free and Pro are separate plugins.** There is no Pro plugin yet, but the contract it will use
   already exists and is tested: `sobol_safe_save_modules`, `sobol_safe_save_register_modules`, `sobol_safe_save_loaded`,
   `sobol_safe_save_should_check`, `sobol_safe_save_report`, `sobol_safe_save_analysis_complete`,
   `sobol_safe_save_settings_defaults`, `sobol_safe_save_settings_sanitize`, plus the `sobol-safe-save` JavaScript store
   and the `sobol_safe_save.report` action. Reaching into internals is a bug, not a shortcut.
5. **The free edition must never be able to block a save.** Guideline 5 of the WordPress.org
   directory forbids shipping functionality withheld pending payment, so "prevent save" is not a
   disabled branch here - `lockPostSaving` simply does not exist in this codebase, and
   `ExtensionApiTest::test_the_free_edition_cannot_block_a_save()` fails the build if it appears.
6. **Never replicate WordPress's save filters by hand.** `Core\Analyzer` calls
   `sanitize_post( $postarr, 'db' )`, which is the line `wp_insert_post()` itself calls, precisely
   so that filters beyond KSES - and filters core adds in future releases - are picked up for free.
   A hand-written list of filters reports "nothing will change" for content that visibly changes.
   `AnalyzerFidelityTest` is what keeps the prediction honest; it compares against the database.
7. **Bump `Core\Api::VERSION`** when the extension contract changes.
8. **Editor code is TypeScript, built with Vite** (`./bin/wpx dev` to watch). Do not reintroduce
   `@wordpress/scripts`. `index.asset.php` is generated by the build and must never be hand-edited.
   Scripts that are not blocks live in `plugins/sobol-safe-save/scripts/<name>/` and are built by
   `buildScripts()` in `cli/vite/wordpress-blocks.mjs`.

## Layout

```
plugins/sobol-safe-save/       free edition (WordPress.org)
  src/Core/              the analysis engine and its value objects
  src/Modules/           editor, rest, settings
  scripts/               editor sources in TypeScript (editor/, shared/)
  build/                 build output (generated, never edited)
  EXTENDING.md           the contract a paid add-on builds on
themes/                  local themes, mounted like the plugins
cli/, bin/wpx            the environment CLI
cli/vite/                the block build
env/                     Dockerfile, entrypoint, compose renderer input
dashboard/               local web dashboard
tests/e2e/               Playwright specs (free/ and pro/)
templates/features/      archived modules for wpx feature add - including `classic`, which is
                         complete and passing but held back until it has e2e coverage
wp-matrix.json           WordPress versions and themes to test against
starter.json             plugin identity, editions, features, skills, lab source
```

## Before calling work done

```bash
./bin/wpx test lint analyse types --targets=latest
./bin/wpx test unit integration --targets=latest,min
./bin/wpx test e2e --targets=latest                  # sweeps the themes
./bin/wpx test plugin-check --targets=latest
```

The end-to-end suite needs two users and creates both: an administrator to reach the settings
screen, and an author, because on a single site an administrator holds `unfiltered_html` and this
plugin has nothing to say to them. A test written as an administrator passes whether or not the
plugin works.

Generated files (`env/docker-compose.gen.yml`, `plugins/*/build/`, `.wplab/`) are never edited by
hand - regenerate them instead.
